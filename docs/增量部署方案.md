# 资源权限申请增量部署方案

## 变更内容

新增独立工作流类型 `4（资源权限申请）`、申请表 `resource_permission_apply`、页面访问/提交权限 `sql.resource_permission_apply`，复用审批权限 `sql.query_review`。最终审批通过后以幂等方式将申请人加入目标资源组。

## 部署前检查

1. 备份业务数据库。
2. 确认应用版本与本次代码一致。
3. 确认 `Default`、`RD`、`PM`、`QA`、`DBA` 中实际需要授权的组；增量 SQL 默认向这些组授予页面访问和提交权限。
4. 检查每个有效资源组已有查询权限工作流配置：

```sql
SELECT rg.group_id, rg.group_name, was.audit_auth_groups
FROM resource_group rg
LEFT JOIN workflow_audit_setting was
  ON was.group_id = rg.group_id AND was.workflow_type = 1
WHERE rg.is_deleted = 0;
```

类型 `4` 使用独立配置。增量 SQL 仅以类型 `1` 的审批节点作为初始化模板，不会在运行时复用类型 `1`。

## 部署步骤

1. 停止 Web 和异步任务进程，保留数据库服务。
2. 部署本次代码。
3. 执行：

```bash
mysql -h <host> -u <user> -p <database> < src/init_sql/resource_permission_apply.sql
```

4. 对没有类型 `1` 配置的有效资源组，按实际审批组补充类型 `4` 配置：

```sql
INSERT INTO workflow_audit_setting
(group_id, group_name, workflow_type, audit_auth_groups, create_time, sys_time)
VALUES (<group_id>, '<group_name>', 4, '<逗号分隔的auth_group.id>', NOW(6), NOW(6));
```

5. 执行应用检查和定向测试：

```bash
python manage.py check
python manage.py makemigrations --check --dry-run
pytest -q sql/test_resource_permission.py
```

6. 启动 Web 和异步任务进程。
7. 使用没有任何资源组的普通用户验证：菜单可见、有效资源组可加载、可提交申请。
8. 使用目标资源组当前审批节点成员验证审批；最终通过后检查用户资源组关系。

## 验证 SQL

```sql
SELECT codename FROM auth_permission
WHERE codename = 'resource_permission_apply';

SELECT g.name
FROM auth_group g
JOIN auth_group_permissions gp ON gp.group_id = g.id
JOIN auth_permission p ON p.id = gp.permission_id
WHERE p.codename = 'resource_permission_apply';

SELECT group_id, group_name, workflow_type, audit_auth_groups
FROM workflow_audit_setting
WHERE workflow_type = 4;

SELECT apply_id, group_id, group_name, user_name, status, create_time
FROM resource_permission_apply
ORDER BY apply_id DESC LIMIT 20;
```

审批最终通过后，可按项目实际多对多中间表名验证用户与资源组关系；建议通过 Django shell 验证以避免不同环境表名差异：

```bash
python manage.py shell -c "from sql.models import Users; u=Users.objects.get(username='<username>'); print(list(u.resource_group.values_list('group_name', flat=True)))"
```

## 回滚方案

先回滚应用代码，再按需执行以下 SQL。回滚会删除申请记录，执行前必须确认已经备份。

```sql
START TRANSACTION;
DELETE FROM workflow_audit_setting WHERE workflow_type = 4;
DELETE gp FROM auth_group_permissions gp
JOIN auth_permission p ON p.id = gp.permission_id
WHERE p.codename = 'resource_permission_apply';
DELETE FROM auth_permission WHERE codename = 'resource_permission_apply';
DROP TABLE IF EXISTS resource_permission_apply;
COMMIT;
```

已审批通过产生的用户资源组关系属于业务授权结果，回滚脚本不会自动删除，避免误删用户通过其他方式获得的权限；如需撤销，应逐条审计后处理。

## 已知约束

- 同一用户的提交流程通过用户行锁串行化，并在事务内检查同用户、同资源组待审批记录。MySQL 不支持通用的条件唯一约束，因此增量 SQL 使用复合查询索引而非把所有历史状态做唯一约束。
- 审批期间目标资源组若被软删除，最终授权会失败并回滚该次审批事务，需要管理员恢复资源组或处置申请。
- 通知由 Django-Q 在事务成功提交后发送；通知失败不会回滚已提交的申请或审批结果。
